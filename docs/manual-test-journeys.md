# Ручные journey — что проверять вживую и что означает провал

Всё в `tests/` headless: логика исполняется, но без композитора. Перечисленное ниже —
изменения в **paint-пути и пути ввода**, которые headless не видит по определению.
Ни одна строка этого файла не была выполнена: на момент написания живой сессии нет.

## Подготовка (один раз)

```bash
cmake --build build -j$(nproc)          # .so свежая — судить по дате, не по выводу
cmake --build build --target reload     # без этого дальше бессмысленно
```

В Lua-конфиге, **до** прогона:

```lua
hl.config({plugin={gloview={debug_trace=1}}})
```

Без `debug_trace` записи `LIFE|`, `DRAG|`, `SCROLL|` не пишутся, и кейсы 1–4
превращаются в «ничего не видно» — это не результат, а отсутствие наблюдения.

Лог: `/tmp/gloview.log`. Утилита: `python3 tools/runtime_check.py --list`.

## J1. Открытие: парковка и выход на экран

**Что проверяет:** `model::Lifecycle`. `open()` обязан припарковать овервью
(`LIFE|park`), дождаться готового бэкдропа и только потом показать (`LIFE|promote`).

| | |
|---|---|
| Предусловие | ≥2 окна на воркспейсе, обои обычные (не видео) |
| Шаги | `hl.plugin.gloview.cmd("open")`, смотреть лог |
| Ожидается | в логе `LIFE|park|own=parked|opening=0|parkTicks=0`, затем `LIFE|promote|own=screen|opening=1`, по порядку |
| Визуально | **первый видимый кадр овервью НЕ чёрный**. Парковка означает «ничего не рисуем», а не «рисуем чёрное» |
| Провал значит | `park` без `promote` → овервью не появилось; `promote` без `park` → первый кадр ушёл без бэкдропа, это ровно тот чёрный кадр, ради которого парковка и существует |

## J2. Видео-обои: парковка не должна зависать

**Что проверяет:** бюджет парковки — 2 кадра, потом открывается в любом случае.

| | |
|---|---|
| Предусловие | обои — видео (mpv/shader, `animation = fps`) |
| Шаги | `cmd("open")` |
| Ожидается | `LIFE|park`, затем `LIFE|promote`, **в любом случае**. Счётчик кадров парковки в `debug_trace` не виден — см. ниже |
| Провал значит | `promote` не наступил → овервью застряло невидимым, а овервью «владеет экраном», то есть окна потеряли фокус и всё заморожено |

> **Про `parkTicks` в J1/J2.** Запись `LIFE|park` эмитится сразу после `requestOpen()`,
> поэтому в ней `parkTicks=0` **всегда**. После `parkTick()` записи `LIFE|` не
> эмитится вовсе, а `describe()` у уже видимого овервью поле `parkTicks` не печатает.
> Фактическое число паркованных кадров видно только в кадровом логе:
> `prime: promote ticks=N backdrop=0/1` — и то под `debug_logs`, а не `debug_trace`.
> Так что проверять бюджет по трейсу нельзя; проверяется только **факт наступления
> `promote`**. Если нужен сам счётчик — включать `debug_logs` и смотреть эту строку.

## J3. Закрытие без прозрачного кадра

**Что проверяет:** правило №9 — деактивация не в середине кадра, иначе один прозрачный кадр.

| | |
|---|---|
| Предусловие | овервью открыто и **видно** (не парковано) |
| Шаги | `cmd("close")`, смотреть лог |
| Ожидается | `LIFE|requestDeactivate`, затем `LIFE|deactivate`. В `LIFE|requestDeactivate` есть `deactivating=1`, в `LIFE|deactivate` — уже нет |
| Визуально | между закрытием плиток и возвратом рабочего стола **нет ни одного прозрачного кадра** — десктоп проявляется сразу под блюром |
| Провал значит | `deactivate` без `requestDeactivate` → овервью снят в тот же кадр; если между кадрами виден «голый» десктоп с резкими окнами — это он |

## J4. Фокус на паркованных кадрах

**Что проверяет:** правило №10 — паркованный овервью **уже владеет экраном**, окна должны потерять фокус на первом паркованном кадре, а не когда овервью появится.

| | |
|---|---|
| Предусловие | сфокусировано окно A; овервью закрыто |
| Шаги | открыть овервью и **не ждать его появления** — сразу нажать клавишу, привязанную к окнам |
| Ожидается | пасc-through работает по окну, которое было сфокусировано **до** открытия, а не по текущему фокусу композитора |
| Провал значит | поле `m_focusOutside` мертво (см. комментарий в `overview.hpp`), так что если поведение неверное — причину надо искать здесь. Это **не** проверка на регресс после разбиения, это проверка несуществующей гарантии |

## J5. Скролл стрипа и сужение полосы

**Что проверяет:** `model::ScrollState::setMax()` переклампивает текущую позицию. До типа её не переклампивал никто — полоса, потерявшая карточку во время скролла, оставалась прокрученной дальше края.

| | |
|---|---|
| Предусловие | достаточно карточек, чтобы `scrollable=1` |
| Шаги | открыть овервью; колесом прокрутить стрип **до конца**; не отпуская колесо, вызвать `cmd("allws 2")` |
| Ожидается | `SCROLL|setMax|scrollable=...`, и **во всех** `SCROLL|` строках `current ≤ max` и `current ≥ 0` |
| Визуально | полоса не уехала за своё крайнее положение, последняя карточка не пропала |
| Провал значит | `current > max` в `SCROLL|setMax` → именно тот баг, который тип закрывает |

## J6. Перетаскивание: одно отпускание — одна ветка

**Что проверяет:** `model::DragT`. Раньше 14 публичных полей читались из семи файлов, и «`Press::Tile` несёт `idx`» было фактом о порядке присваиваний.

| | |
|---|---|
| Предусловие | ≥2 окна |
| Шаги | перетащить плитку ЛКМ и отпустить; повторить ПКМ |
| Ожидается | на **каждое** отпускание ровно одна `DRAG|release|...` и **хотя бы одна** `DRAG|branch|name=...`. Имена веток разные (`Tile->killZone`, `Tile->carouselFocus`, …) |
| Визуально | карточка едет за курсором, точка захвата не «уезжает» (тащишь за угол — тянется за углом) |
| Провал значит | `release` без `branch` → отпускание не решило, что делать; **две** ветки на одно отпускание → потерянная пара press/release, ФСМ обойдена стороной |

## J7. Двойной клик по стрипу

**Что проверяет:** пара `m_pendingClickWin` + `m_clickTimer`. Пара живёт в одном файле, тип ей не достался — но инвариант «таймер и окно ставятся и снимаются вместе» стоит проверить вручную, потому что автоматикой не проверяется.

| | |
|---|---|
| Шаги | один клик по окну в стрипе, дождаться закрытия; затем **быстро** два клика по другой карточке |
| Ожидается | первая одиночная отмена, вторая пара закрывает |
| Провал значит | таймер срабатывает после смены карточки → закрывает не ту; или не срабатывает вовсе → двойной клик мёртв |

## J8. `ws_enter_style`: все четыре значения

**Что проверяет:** `anim::WsStyle`. Неизвестное имя теперь даёт `slide` (дефолт `kRows`), а раньше промахивалось мимо всех веток и тихо уезжало в путь `pop`.

| | |
|---|---|
| Предусловие | ≥2 окна на соседних воркспейсах |
| Шаги | `cmd("set ws_enter_style slide")` → переключить воркспейс; затем `slidevert`; затем `fade`; затем `pop` |
| Ожидается | команда отвечает `CMD\|ok`, **не** `set: unknown key`. Визуально: slide — плитки входят сбоку, slidevert — сверху, fade — проявляются, pop — уменьшенные и растут |
| Провал значит | `unknown key` → `_style` снова не принимается `setTuning`, и `style("ws_enter")` читает ключ, который никто не пишет. Все четыре значения дают одно и то же → `parseWsStyle` резолвит не туда |

> Проверено по коду до написания этого кейса: `setTuning` принимал `_style` только для
> трёх захардкоженных имён (`grid_swap_style`, `strip_swap_style`, `jump_style`), а
> `style()` читает `overridden("<row>_style")` для **каждой** строки с `hasStyle`. То есть
> `ws_enter_style` был читаемым, но недоступным для записи — тот же класс, что
> `grid_swap_style`, на уровень ниже. Починено, `anim_styles` теперь проверяет правило
> «у каждой строки со стилем `<row>_style` записываем».

## J9. Хуки после разбиения `session.cpp`

**Что проверяет:** разбиение на три TU — самая дорогая часть, ошибка стоит сессии.

| | |
|---|---|
| Шаги | открыть овервью; убедиться, что окна **под** овервью не получают фокус мышью и клавиатурой; закрыть |
| Ожидается | `shouldRenderWindow` и `setPointerFocus`/`setKeyboardFocus` работают: клик по овервью не уходит в окно под ним |
| Провал значит | `initialize()` вернул false → хуки не встали. Симптом — «конфиг не подхватился», тот же, что у отсутствующего `extern "C"`. **Немедленно** `ctest -R hook_signatures` |

## J10. Регрессия: guard на immediate-mode вызовы

**Что проверяет:** `draw_sites` уже ловит это статически, но он грепает символы. Вживую проверяется, что guard работает на субпиксельных боксах — там, где `pxb()` округляет и бокс меньше полупикселя становится нулём.

| | |
|---|---|
| Предусловие | карусель с узкой полосой; монитор с дробным масштабом (1.25/1.5) |
| Шаги | открыть карусель; быстро переключать соседние карточки, пока бокс анимируется |
| Ожидается | ни одного пропущенного кадра, ни «дырок» в рамках, ни зависания |
| Провал значит | **краш всей сессии**. Это единственный кейс в файле, где провал невосстановим |

## Если кейс упал

1. `ls -t ~/.cache/hyprland/hyprlandCrashReport*.txt | head -1` — **до** любых догадок.
2. Имя функции в отчёте может быть выдуманным: после hot-reload символизатор резолвит адрес по старой сборке. Сверять `nm -DC build/gloview.so`.
3. `tail -100 /run/user/$(id -u)/hypr/$(ls -t /run/user/$(id -u)/hypr | head -1)/hyprland.log`
4. **Не** запускать `hyprctl --verify-config`: роняет композитор и подсовывает чужие core-дампы.
5. Не делать `rm -rf /run/user/$(id -u)/hypr/*` — вместе с мусором уходят логи живых сессий.
